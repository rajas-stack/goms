# GOMS Production Security Audit — 2026-08-26

**Scope:** A focused pass over `apps/api/src` (the only backend surface), `infra/`, and root config, checking for the specific categories requested: hardcoded secrets, unsafe CORS, unsafe SQL construction, missing input validation, missing transaction boundaries, dangerous destructive operations, error messages leaking sensitive information, improper trust of client-supplied IDs/roles, missing authorization boundaries, insecure file/storage handling. One concrete issue was found and fixed, with regression tests; everything else was reviewed and found to already be handled correctly, or is explicitly not applicable until auth ships (tracked separately in `2026-08-26-goms-production-security-readiness.md`).

## Fixed

**Raw database error messages could reach the client in production.** Every router's `catch (e) { await client.query('ROLLBACK'); throw e }` blocks (used wherever a mutation needs a multi-statement transaction — `commercial.ts`, `sales.ts`, `opportunities.ts`, `hierarchy.ts`, `employees.ts`, `ownership.ts`) rethrow the original error unmodified when it isn't already a deliberately-thrown `TRPCError`. tRPC auto-wraps any such uncaught error as `INTERNAL_SERVER_ERROR` and — by its own default `getErrorShape` — sets the client-visible `message` to that error's raw `.message`, which for a `pg` driver error can be things like a connection failure naming an internal host, or a constraint-violation message naming a table/column. `NODE_ENV=production` (`apps/api/Dockerfile:16`) already suppressed the stack trace, but not the message itself.

**Fix:** `apps/api/src/trpc.ts` now defines `initTRPC.create({ errorFormatter })` — when `error.code === 'INTERNAL_SERVER_ERROR'`, the client-visible message is replaced with a generic `'Internal server error'`; every other error code (the `BAD_REQUEST`/`NOT_FOUND`/`CONFLICT` messages routers deliberately throw, e.g. `"Code already used by another row"`) passes through unchanged, since those are meant to be read by the client. `apps/api/src/app.ts`'s `fastifyTRPCPlugin` registration adds an `onError` hook that logs the real error (via `app.log.error`, including `error.cause`) so an on-call engineer can still diagnose the actual cause from server logs — sanitizing the client response doesn't mean losing the information server-side.

Confirmed safe for the existing test suite: every router test calls procedures via `appRouter.createCaller({})` (a direct, in-process caller), which never goes through tRPC's HTTP error-shaping layer — only `apps/api/src/app.test.ts`'s real `app.inject()`/HTTP-based tests exercise `errorFormatter`, so no router test's assertions on specific business-error messages (e.g. `.rejects.toThrow('already used')`) were affected.

**Regression tests** (`apps/api/src/app.test.ts`, new `describe('error sanitization', ...)` block):
- Mocks `pool.query` to reject with a raw driver-style message (a fake connection-failure string naming a host/user) and confirms the client-visible HTTP response is the generic message, not the raw one.
- Confirms a genuine `BAD_REQUEST` (zod input-validation failure on `customers.get`, no DB dependency) still reaches the client with its real message — proving the fix is scoped to `INTERNAL_SERVER_ERROR` only, not a blanket message-stripping change.

Also fixed in the same pass, found while verifying `apps/api`'s own `tsc -p tsconfig.json` build (not previously part of any gate — `npm --workspace apps/api run build` was failing before this pass, independent of the security fix): two pre-existing implicit-`any` / missing-DOM-lib-type errors in `app.ts`'s new `onError` callback and `app.test.ts`'s `injectFetch` test helper. Fixed with explicit types (`{ path?: string; error: TRPCError }`, and `ConstructorParameters<typeof Headers>[0]` in place of the DOM-only `HeadersInit`) rather than adding a `"dom"` lib to a Node-only backend tsconfig.

## Reviewed, no fix needed

- **Hardcoded secrets/credentials:** none found anywhere in `apps/api/src`, `infra/`, or root config (grepped for password/secret/apiKey literals and common key-prefix patterns). Real secrets are Secret-Manager-referenced in Terraform, never literals.
- **Unsafe CORS:** `apps/api/src/app.ts` uses an explicit allow-list (`DEFAULT_ALLOWED_ORIGINS` merged with `CORS_ALLOWED_ORIGINS`), never `origin: true`/`*`.
- **Unsafe SQL construction:** parameterized (`$1, $2, ...`) throughout via the `pg` library — no string-concatenated user *values* anywhere. Six places build a dynamic `UPDATE ... SET` clause by interpolating **column names** (not values) into the SQL string (`employees.ts:343,430`, `commercial.ts:519,958`, `opportunities.ts:131`, `sales.ts:99`) — reviewed specifically because it's a less-common pattern than pure parameterization. Not exploitable: the interpolated names are drawn from fixed lookup tables (e.g. `employeeColumnFor`, `skuColumnFor`) keyed by `Object.keys(input.patch)`, and `input.patch` is validated by a `z.object(...)` shape first, which strips any key not in that closed, whitelisted set by default — a client cannot inject an arbitrary column name this way.
- **Missing input validation:** every mutation has a `z.object(...)` input schema; no bare `z.any()`/unchecked input found on a mutation path.
- **Missing transaction boundaries:** every multi-statement write already uses an explicit `BEGIN`/`COMMIT`/`ROLLBACK` block. The two router files with no `BEGIN` anywhere (`customers.ts`, `follow-ups.ts`) were checked specifically — every mutation in both is exactly one `pool.query(...)` call, which Postgres already executes atomically; there's nothing to coordinate, so no transaction is missing.
- **Dangerous destructive operations:** every `DELETE` in non-test application code is scoped by a parameterized `WHERE id=$1` (or `WHERE ... = ANY($1)` over an explicit id list, `hierarchy.ts`'s cascade-delete-subtree path) — no unbounded `DELETE FROM table` or `TRUNCATE` exists outside test-cleanup code (which only ever runs against the disposable test database, never production).
- **Insecure file/storage handling:** not applicable — no file-upload or Cloud Storage-touching code exists anywhere in `apps/api/src` today. The `${project_id}-attachments` bucket exists only in Terraform, unused by any application code yet.

## Explicitly deferred, not a gap in this pass

- **Improper trust of client-supplied IDs/roles** and **missing authorization boundaries** — genuinely not applicable *today*, since there is no auth of any kind yet (every procedure is `publicProcedure`, a fact this pass re-confirmed by grep, not assumed). IDs are validated for format (`z.string().uuid()`) and existence (explicit FK-existence checks), but not ownership — because there's no concept of an owner yet. This is exactly the surface that changes once auth ships, and is mapped out precisely (which routers, which procedures, in what order) in `2026-08-26-goms-production-security-readiness.md` rather than guessed at here.
