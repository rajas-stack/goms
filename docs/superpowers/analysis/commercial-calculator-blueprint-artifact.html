Key findings up front

This module already went through a full business-logic reverse-engineering pass and two rounds of IA redesign on 2026-08-03 — the current live nav (Dashboard / Create BOQ / BOQ Management / Catalog / Settings) is the direct, stakeholder-confirmed output of that work. Requirement #1 reopens a decision that round explicitly made.

#RequirementFinding
01Move SKU Catalog / Product Editions under SettingsDirectly reverses IA review round 2's confirmed reasoning: Commercial/Product Ops treats these as daily work, not admin config, and a permission boundary was the whole point of splitting them from Settings. See Open Question 1 before implementing as literally stated.
02Show SKU pricing before adding to a proposalCreateBoq.tsx's picker resolves a SKU and shows code/name/tax% — but never list price, discounted unit price, or line total until after "Add to Proposal" is clicked.
03Remove Recent Activity; verify Audit LogAuditLog.tsx already exists under Settings, reading the same data Dashboard's block duplicates. All three audit entity types (boq/sku/feature) are captured — but the filter dropdown only offers All/BOQ/SKU, missing an explicit "Feature" option.
04Customer selected from AMNEX stakeholder dataA real source already exists: "Department" is a government-org HierNode, and Employee records under it (useEmployeesUnder) are real stakeholder contacts, already surfaced elsewhere via EmployeePicker.tsx. Create BOQ's Customer section is still 100% disconnected free text.
05Fix "approved BOQs still show under Pending Approval"Traced isBoqPendingApproval, BOQ_TRANSITIONS, the document-level approval gate, and every query invalidation — all correct as of 73ebe732. Strongest lead: the Android bundle is 8+ days stale relative to source (see §8).
06Draft-live / frozen-on-submit / dashboard refreshAlready implemented — withLiveDraftPricing/withLiveDraftGrandTotal landed in yesterday's commit. This item only needs regression protection while the other five are touched.

05

Step-by-step use cases

Each: starting point → actions → expected result. Written to be run as manual test cases once implemented — click a row to expand.

UC1 Create a BOQ
Start
Dashboard → "+ Create New BOQ"
Actions
Fill Opportunity/Department/Vertical/Currency/Sales Person → fill Customer (UC2) → add a line (UC3) → Save Draft.
Expect
Toast confirms save; redirected to /boq/:boqId; appears in Dashboard's "Continue Draft" and BOQ Management as Draft.
UC2 Select customer from AMNEX stakeholder data req #4
Start
Create BOQ, Department already selected.
Actions
Open the Stakeholder Contact picker → search a name → select a real Employee under that Department.
Expect
Organization fills from the Department name; Contact name/phone/email fill from the Employee; Address prefills (editable); nothing is typed from scratch. Changing Department refilters candidates.
UC3 Select SKU and review pricing before adding req #2
Start
Create BOQ, Vertical selected.
Actions
Pick Product → Module → Feature until a SKU resolves → set Qty/Discount → read the Pricing Preview → Add to Proposal.
Expect
Preview shows List Price, discounted unit price, tax%, and line total before Add — matching the committed line exactly.
UC4 Submit a BOQ
Start
An open draft with ≥1 line, required fields filled.
Actions
Save & Submit, or open the draft and click "Submitted".
Expect
Status → submitted; audit entry written; leaves "Continue Draft"; appears in "Pending Approvals" + KPI.
UC5 Approve a BOQ
Start
A BOQ in under_review, all lines auto-approved or resolved.
Actions
Open detail → click "Approved" → enter reason.
Expect
Status → approved; audit entry written; disappears from "Pending Approvals", appears in "Recently Approved" on the very next render — no manual refresh.
UC6 Reject a BOQ
Start
A BOQ in under_review.
Actions
Click "Rejected" → enter reason.
Expect
Status → rejected; appears in "Recently Rejected"; a "Revise" button now appears.
UC7 Approve gate blocks an unresolved line, then clears it
Start
A BOQ in under_review with ≥1 line requiring manual approval.
Actions
Click document-level "Approved" first (expect block) → go to Approvals tab, set Approver, click Approve on the line → retry document-level Approved.
Expect
First attempt fails with a count of pending lines; second attempt succeeds once every line is auto_approved or approved.
UC8 Verify an approved BOQ leaves Pending Approval req #5
Start
Complete UC5 on npm run dev — not the Android build.
Actions
Return to Dashboard without refreshing the tab.
Expect
Not present in "Pending Approvals"; KPI decremented. If it fails only on-device, the cause is the stale mobile bundle, not the web code.
UC9 Manage SKU through Settings
Start
Settings → Catalog group → SKU Catalog.
Actions
"+ New SKU" → fill required fields → save.
Expect
Appears in the list; audit entry written; immediately selectable in Create BOQ's picker once active + sellable.
UC10 Manage Product Editions through Settings
Start
Settings → Catalog group → Product Editions.
Actions
Open an Edition → Features → toggle mandatory/optional → save.
Expect
Mapping persists on reopen. Still reference-only downstream today — see Open Question 4.
UC11 Review Audit Log req #3
Start
Settings → Audit Log.
Actions
Perform one SKU edit, one Feature status change, one BOQ transition → filter by each entity type, then "All".
Expect
All three appear with correct field/old/new/reason/timestamp. Filtering specifically for the Feature change needs "All" today unless the dropdown gains that option.
UC12 Change SKU price — draft vs. submitted behavior req #6
Start
One draft BOQ and one submitted+ BOQ, both referencing the same SKU.
Actions
Settings → SKU Catalog → edit that SKU's List Price → save.
Expect
Draft BOQ's line reflects the new price. Submitted BOQ's line is unchanged — still the value captured at add-time. Dashboard's Value/Margin KPIs update without a manual refresh.

08

Open questions

1

Does req #1 mean fully dissolving the Catalog tab, reversing IA review round 2 — or something narrower? The user's example sitemap lists only SKU Catalog, Product Editions and Audit Log under Settings, omitting Hierarchy, Approval Matrix, Reference Data entirely. Three readings are possible, from "fold everything in, Catalog disappears" to "only relocate two screens, everything else stays put." Needs an explicit decision before writing the implementation plan.

2

Where was the pending-approval bug actually observed — browser or Android app? The Android bundle is 8+ days stale relative to source and current code shows no defect; this changes whether any code change is needed at all.

3

Does GST make sense for a government-department customer? CommercialBoq.customerGst is a private-company concept with no equivalent on the HierNode/Employee records req #4 points at. Decide whether it stays free text, gets dropped, or needs a new optional field — without inventing a new master.

4

Should Product Editions' Feature mapping become enforced as part of this round, since its screen is the one being relocated — or stay reference-only, as today? Worth an explicit "not in scope" confirmation.

5

Should the req #4 customer picker allow creating a new stakeholder inline (a first-time government contact)? EmployeePicker.tsx already supports this via its optional onCreate prop — confirm whether to wire it in now or defer, since it's the one place req #4 could quietly grow scope.
